## 1. 产品愿景与一句话定位

**一句话定位**：vul-labs 是一个**开源、可 Docker 一键自托管**的漏洞靶场平台，让用户在**隔离沙箱**中安全地学习、复现和训练各类 Web/系统漏洞。

**愿景**：成为中文社区最易上手、最易自部署的开源安全练习平台——降低安全学习的环境门槛，把"搭环境"的时间还给"学攻防"。

**核心价值主张**：
> vul-labs 帮助安全学习者**在 5 分钟内拥有一个可被攻击的真实漏洞环境**，而无需自己折腾依赖、配置和隔离——点开靶场、一键启动容器、提交 flag、看到进度。

## 2. 目标用户与典型场景

### 画像 A：安全初学者 / 自学者（主要画像）
- **是谁**：在校学生、转行做安全的工程师、对 Web 安全好奇的开发者。
- **痛点**：想学 SQL 注入/XSS 但不会搭环境；网上教程环境老旧、跑不起来；不敢在真实站点上练（违法）。
- **场景**：晚上想练手 → 打开 vul-labs → 选"SQL 注入-入门" → 一键启动 → 跟着提示尝试 → 提交 flag → 看到自己通关。
- **成功定义**：30 分钟内独立完成第一个靶场并提交 flag。

### 画像 B：CTF 选手 / 安全竞赛训练者
- **是谁**：高校 CTF 战队成员、想刷题保持手感的安全从业者。
- **痛点**：需要可重复、可计分、能反复重置的训练环境；希望按漏洞类型/难度筛选刷题。
- **场景**：赛前集训 → 按"难度=中等 + 类型=SSRF"筛选 → 连续打多个靶场 → 通过计分和进度评估水平。
- **成功定义**：能按类型/难度高效刷题，进度和得分可量化。

### 画像 C：高校教师 / 企业安全培训负责人
- **是谁**：开设安全课程的老师、负责内部红蓝对抗培训的安全团队 Leader。
- **痛点**：要为几十名学员提供**隔离、互不干扰、可控成本**的练习环境；自建维护成本高。
- **场景**：课程前自托管部署 vul-labs → 学员各自注册 → 每人独立启动实例互不影响 → 通过进度/排行观察学习情况。
- **成功定义**：一次部署支撑全班练习，实例互相隔离，不会一人搞崩全班。

> 说明：画像 C 的"多租户教学管理（班级/批量账号/作业）"是强需求但**非 MVP**，MVP 先满足"自托管 + 每人独立隔离实例"这一最小闭环。

## 3. 竞品 / 参考对比与差异化定位

| 维度 | DVWA / Pikachu | VulHub | 在线 CTF 平台（如 CTFd 部署的赛事） | **vul-labs（本产品）** |
|------|----------------|--------|------------------------------|----------------------|
| 形态 | 单体靶场应用 | 漏洞环境合集（compose 仓库） | 计分/赛事平台 | **平台 + 按需容器靶场 + 计分一体** |
| 环境隔离 | 单实例、多人共用 | 手动各自起 compose | 通常需另配靶机 | **按用户/按需启动独立容器实例** |
| 计分/进度 | 无 | 无 | 有计分，无内置靶场 | **内置 flag 校验 + 计分 + 个人进度** |
| 上手成本 | 低但环境老旧 | 中（需懂 docker-compose） | 中高（搭平台 + 配题） | **一键自托管，开箱即用** |
| 引导性 | 弱 | 无 | 取决于出题人 | **靶场带分类/难度/提示** |
| 自托管开源 | 是 | 是 | 部分是 | **是（核心约束）** |

**差异化定位**：vul-labs = **"VulHub 的丰富靶场" + "CTFd 的计分进度" + "DVWA 的开箱即用"** 三者的最小可行结合体，且把**按需实例化与沙箱隔离**作为一等公民。我们不做"最全漏洞库"，先做"最顺滑的练习闭环"。

**我们明确不做（差异化的反面）**：不做完整赛事/积分赛系统、不做漏洞情报库、不做企业级 SSO/LDAP（这些留给后续或集成）。

## 4. MVP 范围（做什么 / 不做什么）

### MVP 要做（P0，构成一条端到端闭环）
1. **用户注册 / 登录 / 登出**（本地账号，邮箱或用户名 + 密码）。
2. **靶场列表与分类筛选**（按漏洞类型、难度筛选）。
3. **靶场详情页**（描述、目标、难度、提示、启动入口）。
4. **按需启动 / 销毁靶场实例**（每次启动一个独立容器，提供访问地址，超时自动销毁）。
5. **提交 flag 与计分**（服务端校验 flag，正确则计分并记录通关）。
6. **个人进度**（已通关靶场、总得分、最近活动）。

### MVP 漏洞类型覆盖（先选 3 个经典 Web 漏洞做深做透）
- **SQL 注入**（入门）
- **反射型 XSS**（入门）
- **文件上传**（中等）

> 选择理由：这三类覆盖"注入 / 客户端 / 服务端文件处理"三种典型攻击面，教学价值高、容器化简单、flag 校验直观。**SSRF、命令注入**列入 P1 紧随其后（见 backlog），不在第一批靶场内以控制范围。

### MVP 暂不做（明确说"不"）
| 不做项 | 原因 | 重新考虑条件 |
|--------|------|------------|
| 排行榜 / 社交 | 闭环可不依赖它 | 核心闭环上线且有活跃用户后（P2） |
| 班级 / 多租户教学管理 | 范围翻倍 | 画像 C 验证有真实部署需求后 |
| 第三方登录 / SSO | 本地账号已够用 | 企业用户接入诉求出现时 |
| 提示分级扣分 / 经济系统 | 增加计分复杂度 | 计分基础稳定后 |
| 用户自定义上传靶场 | 安全风险高、范围大 | 平台稳定且有内容贡献需求后 |
| 系统/二进制类漏洞（pwn 等） | 容器化与隔离复杂度高 | Web 类靶场体系成熟后 |
| 多语言 i18n | 先服务中文社区 | 海外贡献者出现时 |

## 7. 非功能需求（NFR）

### 性能
- 靶场列表页首屏加载 < 1.5s（100 个靶场以内）。
- 靶场实例启动：从点击到拿到可访问地址，**P95 < 30s**（受镜像拉取影响，已拉取镜像应 < 10s）。
- Flag 提交校验响应 < 500ms。

### 安全（平台面，必须安全）
- 密码加盐哈希存储（bcrypt/argon2），禁止明文。
- 会话使用 HttpOnly + SameSite Cookie 或安全 Token；防 CSRF。
- 所有"平台 API"做鉴权与越权校验（用户只能操作自己的实例与进度）。
- Flag **服务端校验**，前端绝不下发正确答案；提交接口限流防爆破。
- 平台自身代码遵循安全编码（参数化查询、输出编码等）——平台不能有真实漏洞。

### 隔离（沙箱，产品级硬要求）
- 每个靶场实例 = 独立容器；限制 CPU / 内存 / 磁盘配额。
- 靶场容器**禁止访问平台内网、数据库、宿主元数据服务**（网络隔离）。
- 用户间实例不复用、不可互相访问。
- 实例有生命周期：超时（如 60 分钟无活动）自动销毁，防资源耗尽。

### 可部署性 / 可运维
- `docker-compose up` 一键启动整套平台（前端 + 后端 + DB + 实例引擎）。
- 提供默认种子数据（3 个 MVP 靶场可直接用）。
- 关键操作（实例启停、flag 提交）有日志，便于教学与排障。
- 配置（端口、实例超时、资源配额）通过环境变量可调。

### 可用性 / 兼容
- 现代浏览器（Chrome/Firefox/Edge 最新两个大版本）。
- 深色模式优先（贴合安全工具使用习惯，UI 阶段细化）。

## 8. 安全与合规边界（关键章节）

### 8.1 "靶场漏洞 = 预期行为" vs "平台漏洞 = 必须修复"

| 类别 | 定义 | 处理原则 | 示例 |
|------|------|---------|------|
| **靶场内漏洞** | 靶场容器内**刻意设计**的可被攻击点 | **不修复，是功能**；必须沙箱隔离、有明确边界、不可外溢 | 靶场里的 SQL 注入点、可上传 webshell 的上传点 |
| **平台漏洞** | 平台自身（账号/计分/实例编排/API）的安全缺陷 | **必须修复，视为缺陷** | 越权查看他人进度、flag 校验被绕过、SSRF 打到平台内网、容器逃逸 |

> 代码审查与测试阶段必须显式区分二者：靶场内漏洞**不得**被记为平台缺陷；平台漏洞**不得**被当作"靶场特性"放过。每个靶场需在内容元数据中标注其"预期漏洞点"，作为审查/测试的对照基线。

### 8.2 沙箱隔离的产品级要求（验收口径）
1. **网络隔离**：靶场容器只能被发起它的用户访问，不能访问平台后端/DB/宿主元数据（如 169.254.169.254）。
2. **资源隔离**：单实例 CPU/内存/磁盘有上限，避免单靶场拖垮平台。
3. **生命周期**：按需创建、超时销毁、用户间不复用实例。
4. **数据隔离**：靶场内数据销毁随实例回收，不污染平台数据库。
5. **逃逸防护**：容器以最小权限运行（非 root、drop capabilities、禁止特权模式）。

### 8.3 合规与使用边界
- 平台仅供**授权的学习与训练**，靶场环境为隔离沙箱，**禁止用于攻击真实系统**。
- 首页 / 注册需有免责声明与合规提示（"仅限合法授权环境内使用"）。
- 开源协议与靶场内容版权需在仓库声明（License 待定，建议 MIT/Apache-2.0 + 内容单独声明）。

## 9. 成功指标（上线后度量）

| 目标 | 指标 | 度量窗口 |
|------|------|---------|

## 10. 第一迭代建议范围（端到端闭环）

遵循 WORKFLOW "每迭代只交付 1~3 个用户故事完整闭环"的节奏，**第一迭代建议聚焦"单个靶场的最小可玩闭环"**：

**第一迭代（Sprint 1）建议交付**：
1. **US-002 登录**（注册 US-001 可同迭代带出，至少先支持一个可登录账号）。
2. **US-020 启动靶场实例**（先打通 1 个靶场：**SQL 注入-入门**，含容器编排 + 访问地址 + 超时销毁）。
3. **US-030 提交 flag 并计分**（服务端校验 + 通关记录）。

> 即用户可：登录 → 进入 SQL 注入靶场 → 一键启动拿到地址 → 攻击拿到 flag → 提交看到"通关 + 得分"。这是验证"平台技术可行性 + 核心价值"的最小切片。靶场列表/详情（US-010/US-012）与个人进度（US-040）紧随第二迭代补全浏览与回看体验。

**第一迭代的关键风险（需后端/安全在架构阶段先解）**：
- 容器编排与沙箱隔离方案（实例引擎）——这是技术可行性的命门，必须在 G2 由安全工程师确认。
- Flag 服务端校验与防爆破——决定计分是否可信。
